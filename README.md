# Telegram Mini App Shop

Магазин в Telegram с каталогом, корзиной, оформлением заказов и веб-админкой.
Демонстрационная витрина SweetBox показывает сценарий продажи тортов, десертов, наборов и напитков.

Проект подготовлен к запуску через Docker Compose. Клиентские настройки передаются при развёртывании через `.env`.

## Возможности

### Для покупателя

- Главная страница с категориями и популярными товарами.
- Каталог с поиском по названию и фильтром по категории.
- Карточка товара с фотографией, описанием, ценой и выбором количества.
- Корзина с изменением количества, удалением позиций и сохранением в браузере между посещениями.
- Оформление заказа с именем, телефоном и комментарием.
- Список своих заказов с составом, суммой и автоматически обновляемыми статусами.
- Таймер оплаты и переход к оплате по ссылке счёта.
- Telegram-уведомления о принятом после оплаты заказе и изменении статуса, сообщения менеджера.

### Для администратора

| Раздел | Возможности |
|---|---|
| Заказы | Списки «Активные», «Завершённые» и «Все», просмотр состава и контактов покупателя |
| Обработка заказа | Перевод в работу, завершение и отмена с проверкой допустимых переходов статуса |
| Связь с покупателем | Отправка сообщения из карточки заказа в Telegram клиента |
| Товары | Создание и редактирование названия, описания, цены, категории и порядка сортировки |
| Видимость | Публикация и скрытие товара, включение в подборку популярных товаров |
| Остатки | Задание количества и включение учёта остатков отдельно для каждого товара |
| Фотографии | Загрузка при создании товара и замена главного фото при редактировании, предпросмотр |
| Удаление товара | Проверка связей с заказами и вывод номеров заказов, препятствующих удалению |
| Категории | Создание с проверкой уникальности названия и удаление категории после переноса её товаров |
| Навигация по товарам | Фильтр по категории и группировка списка товаров |

Отмена заказа возвращает учитываемые остатки. Автоматический возврат денежных средств
при отмене заказа не выполняется.

### Заказы и оплата

При оформлении бэкенд рассчитывает сумму по актуальным ценам, проверяет остатки и резервирует товары.
Заказ получает статус `AWAITING_PAYMENT` и срок оплаты 30 минут.

Приложение создаёт счёт через Invoice API ЮKassa, сохраняет ссылку, повторно использует
созданный счёт и сверяет его состояние с провайдером в фоновом режиме. После подтверждения оплаты заказ переходит в `NEW`,
становится доступен в активных заказах администратора и запускает отправку уведомлений.
Обработка просроченных заказов и отменённых счетов освобождает резерв.

## Стек и устройство проекта

Java 17, Spring Boot, Spring Security, Spring Data JPA, Hibernate, PostgreSQL 16,
Flyway, MapStruct, Telegram Bot API, ЮKassa API, React, TypeScript, Vite,
JUnit 5, Mockito, Docker Compose, Nginx и GitHub Actions.

Бэкенд организован по функциональным пакетам в `src/main/java/ru/sergeydev/telegramminiappshop`.

| Пакет или каталог | Назначение |
|---|---|
| `product`, `category` | Каталог, остатки, хранение и выдача фотографий |
| `order` | Создание заказов, расчёт суммы, резервирование и статусы |
| `payment` | Подготовка платежа, интеграция с провайдером и фоновая сверка |
| `telegram` | Бот, проверка initData, клиентские запросы и уведомления |
| `admin` | Административные API и настройка доступа |
| `common` | Общая обработка ошибок |
| `frontend/src` | Витрина Mini App и веб-админка |

Сумму заказа бэкенд рассчитывает по ценам из базы. Для изменения остатков используются транзакции
и блокировки товаров в порядке их идентификаторов. Создание заказа и оплаты использует ключи идемпотентности.
Для платежей в базе также задано ограничение на одну попытку в статусе `PENDING` на заказ.

При создании счёта сначала сохраняется попытка оплаты, затем выполняется запрос к провайдеру,
после чего результат сохраняется отдельной транзакцией. Планировщик повторно обрабатывает незавершённые
попытки и сверяет состояние выставленных счетов.

## Запуск через Docker Compose

Потребуются Git, Docker с Compose v2 и доступ к Telegram API. Сборка Java и React выполняется внутри Docker.
На Windows можно использовать Docker Desktop с Linux-контейнерами.

### 1. Подготовка настроек

```bash
git clone https://github.com/s-u-p-e-r-m-a-n/telegram-miniapp-shop.git
cd telegram-miniapp-shop
```

Создайте `.env` в корне проекта, скопировав [.env.example](.env.example).
В PowerShell это можно сделать командой `Copy-Item .env.example .env`, в Linux — `cp .env.example .env`.

| Переменная | Значение |
|---|---|
| `POSTGRES_DB` | Имя базы, создаваемой при первом запуске PostgreSQL |
| `POSTGRES_USER` | Пользователь PostgreSQL |
| `POSTGRES_PASSWORD` | Пароль PostgreSQL |
| `TELEGRAM_BOT_TOKEN` | Токен бота из BotFather |
| `TELEGRAM_ADMIN_CHAT_ID` | Числовой chat ID для уведомлений администратору |
| `TELEGRAM_WEB_APP_URL` | Публичный HTTPS-адрес магазина |
| `ADMIN_USERNAME`, `ADMIN_PASSWORD` | Данные входа в веб-админку |
| `YOOKASSA_SHOP_ID`, `YOOKASSA_SECRET_KEY` | Учётные данные магазина для обращения к API ЮKassa |
| `YOOKASSA_RETURN_URL` | Адрес возврата для альтернативного redirect-сценария в адаптере провайдера. Для текущего Invoice-сценария может быть пустым |
| `WEB_PORT` | Локальный HTTP-порт магазина, по умолчанию `8081` |

Заполните обязательные значения вместо примеров из шаблона.
Параметры ЮKassa можно оставить пустыми для просмотра каталога и работы с админкой.
Для создания счетов нужны учётные данные с доступом к Invoice API.
Текущий сценарий Invoice получает ссылку из ответа провайдера.

Администратор создаётся в памяти приложения из `ADMIN_USERNAME` и `ADMIN_PASSWORD` и получает роль `ADMIN`.
Административные API используют HTTP Basic. Для клиентских запросов бэкенд проверяет подпись
и срок действия Telegram initData. Список заказов выбирается по Telegram ID пользователя,
а перед созданием счёта дополнительно проверяется принадлежность заказа.

При локальной проверке направьте Cloudflare Tunnel на `http://localhost:8081` и запишите выданный
HTTPS-адрес в `TELEGRAM_WEB_APP_URL`. При развёртывании на VPS укажите постоянный адрес магазина.
Настройки читаются при запуске контейнера. После смены адреса обновите бэкенд командой
`docker compose -f compose.release.yml up -d`, затем отправьте боту `/start`, чтобы получить кнопку с новым адресом.

Бот получает сообщения через long polling. Для одного токена запускайте один экземпляр приложения.
Перед проверкой уведомлений администратор должен начать диалог с ботом командой `/start`.

### 2. Сборка и запуск

Выполните из корня проекта.

```bash
docker compose -f compose.release.yml config --quiet
docker compose -f compose.release.yml up -d --build
docker compose -f compose.release.yml ps
```

Compose ожидает готовности PostgreSQL, затем запускает бэкенд и после его успешной проверки — фронтенд.
Бэкенд подключается к `postgres:5432` внутри Docker-сети. Compose сам задаёт JDBC URL и учётные данные
из `POSTGRES_*`.

| Адрес при `WEB_PORT=8081` | Назначение |
|---|---|
| `http://localhost:8081` | Витрина |
| `http://localhost:8081/admin/` | Веб-админка |
| `http://localhost:8081/api/categories` | Публичный API категорий |

Nginx отдаёт собранный React-фронтенд и перенаправляет `/api/` и `/uploads/` на бэкенд.
В Compose порт фронтенда привязан к `127.0.0.1`. Для внешнего доступа используется HTTPS-прокси или туннель.

Для оформления заказа откройте бота в Telegram, отправьте `/start` и нажмите «Открыть магазин».
Просмотр витрины и вход в админку доступны в обычном браузере.

### 3. Остановка и диагностика

```bash
docker compose -f compose.release.yml logs --tail=100 backend
docker compose -f compose.release.yml logs --tail=100 frontend
docker compose -f compose.release.yml down
docker compose -f compose.release.yml up -d
```

Обычный `down` сохраняет именованные тома. `down -v` удаляет их вместе с базой и загруженными фотографиями.

| Том | Содержимое |
|---|---|
| `tma-release_release-db-data` | Данные PostgreSQL, заказы, каталог и ссылки на фото |
| `tma-release_release-uploads` | Загруженные файлы фотографий |

Для резервной копии магазина нужны данные обоих томов. Демофотографии из `frontend/public/images`
попадают в образ фронтенда при сборке. Загрузка пользовательских фото поддерживает JPG, PNG и WebP
с ограничением 5 МБ на файл.

## База и миграции

В проекте два независимых набора миграций.

| Режим запуска Spring | Расположение | Назначение |
|---|---|---|
| Без профиля `release` | `db/migration` | История разработки, 15 миграций |
| Профиль `release` | `db/release` | Установка с нуля, две миграции |

`compose.release.yml` включает профиль `release` автоматически.
`V1__init_schema.sql` создаёт итоговую схему, `V2__insert_demo_catalog.sql` добавляет SweetBox
с четырьмя категориями, восемью товарами и восемью фотографиями.
При первом запуске база содержит демокаталог и пустые таблицы заказов и платежей.

Каждая база должна использовать один набор миграций на протяжении своего существования.
У каждого набора своя история Flyway. Переключение набора для существующей базы требует отдельного
плана переноса. Новые изменения схемы следует учитывать в обоих наборах.

Профиль Spring выбирает настройки и папку миграций, а `SPRING_DATASOURCE_URL` определяет базу подключения.
В конфигурации запуска IDEA эти параметры задаются отдельно.

`docker-compose.yml` используется для локальной разработки и поднимает PostgreSQL с портом из `POSTGRES_PORT`.
Для запуска бэкенда из IDEA используются `SPRING_DATASOURCE_URL`, `SPRING_DATASOURCE_USERNAME`
и `SPRING_DATASOURCE_PASSWORD` из `.env`. Для фронтенда в каталоге `frontend` выполните
`npm ci` и `npm run dev`, используя Node.js 24. Vite перенаправляет API и фотографии на `localhost:8080`.

## Тесты и CI

Два unit-теста проверяют бизнес-логику сервисного слоя. Репозитории и внешние интеграции
заменены Mockito-моками, сервисы выполняют настоящую бизнес-логику.

| Тест | Что проверяет |
|---|---|
| `OrderServiceTest` | Расчёт суммы, начальный статус заказа и уменьшение остатка |
| `PaymentServiceTest` | Подготовку попытки оплаты, данные запроса Invoice и сохранение ответа провайдера |

Запуск на Windows из корня проекта.

```powershell
.\mvnw.cmd -B "-Dtest=OrderServiceTest,PaymentServiceTest" verify
```

Запуск в Linux или macOS.

```bash
bash ./mvnw -B "-Dtest=OrderServiceTest,PaymentServiceTest" verify
```

Для этих тестов достаточно Java 17. Тесты изолированы от базы данных и внешних API:
они не проверяют выполнение SQL, блокировки базы и обмен с платёжным провайдером.
GitHub Actions выполняет эту же проверку для PR в `master` и push в `master`.
Docker-сборка бэкенда использует `-DskipTests`; проверка тестов выполняется отдельно в CI.

## Эксплуатация

Для запуска магазина на сервере задайте постоянный HTTPS-адрес, параметры бота,
учётные данные администратора и магазина ЮKassa через `.env`.
Настройте HTTPS-прокси и резервное копирование базы данных и загруженных фотографий.

Платёжная интеграция использует Invoice API. Доступ к нему и настройка уведомлений
зависят от учётной записи магазина у провайдера. Перед приёмом реальных заказов
проверьте полный платёжный сценарий в целевом окружении.

## Проверки после развёртывания

1. Проверить вход в админку и загрузку фотографии товара.
2. Открыть магазин через Telegram, оформить заказ и проверить остатки.
3. Проверить счёт, успешную оплату, повторный запрос и истечение срока на магазине клиента.
4. Проверить уведомления клиенту и администратору и смену статусов заказа.
5. Проверить резервное копирование и восстановление базы вместе с файлами фотографий.
